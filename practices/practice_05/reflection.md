# Рефлексия по Практике 5: Spec-Driven Development (GitHub Spec Kit vs OpenSpec)

## Сравнение фреймворков

В рамках выполнения 5-й практики мы опробовали альтернативный SDD-инструмент — **GitHub Spec Kit** (`specify-cli`) — и сравнили его с разобранным на семинаре **OpenSpec**.

### Главный вывод:
**Мне показалось, что GitHub Spec Kit слишком замудрён. OpenSpec проще и интуитивно понятнее.**

### Подробное сопоставление:
1. **Сложность тулинга и файловая структура:**
   - **GitHub Spec Kit:** генерирует массивную инфраструктуру файлов (`.specify/`, `memory/constitution.md`, манифесты интеграций, `workflows/`, поддиректории `checklists/`, `research.md`, `data-model.md`, `quickstart.md` для каждой фичи). Для небольшой команды или задачи такой оверхед кажется избыточным и загромождает репозиторий.
   - **OpenSpec:** устроен гораздо лаконичнее и прямолинейнее. Есть понятный жизненный цикл фичи (`proposal.md` -> `design.md` -> `spec.md` -> `tasks.md` -> `apply` -> `archive`) без лишней бюрократии.

2. **Работа AI-агента:**
   - В OpenSpec команды CLI дают компактный и сфокусированный контекст (`openspec instructions`).
   - В Spec Kit агент вынужден резолвить несколько связанных шаблонов и манифестов, что увеличивает время генерации и повышает шанс запутаться в структуре артефактов.

## Опыт эмуляции двух команд и согласования контракта

Эмуляция двух изолированных команд (Команда 1: Frontend UI и Команда 2: Backend Logic) показала главную ценность подхода Spec-Driven Development:

1. **Что помогло:**
   - Фиксация единого контракта (`problem-list-search.md` и `problems-search-api.md`) **до** написания первой строчки кода избавила от рассогласований. Команды заранее договорились об имени query-параметра (`q`), регистронезависимом поиске, возврате HTTP 200 с пустым массивом `[]` (вместо 404 при отсутствии совпадений) и локальном fallback-поведении на фронтенде.
   - Благодаря этому после генерации кода интеграция прошла с первого раза, и проверочный хук `./scripts/verify-tests.sh` (Go unit-тесты + TypeScript/Vite сборка) отработал без единой ошибки.

2. **Итог:**
   - Сам подход SDD с предварительным согласованием контрактов полностью себя оправдывает. Однако в качестве инструмента **OpenSpec** выглядит более практичным и удобным для повседневной разработки, чем тяжеловесный **GitHub Spec Kit**.
